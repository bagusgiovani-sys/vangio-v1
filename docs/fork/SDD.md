    │          │          │          │

Since all four providers speak the same OpenAI-compatible protocol, there's one shared contract, not four separate integrations — the advantage of forking a mature multi-provider tool instead of building from scratch.

## 2. Service Boundaries

- **Terminal/TUI:** rendering, user input — inherited, unmodified
- **Agent core:** decides what to ask the model, executes tool calls (file edits, shell commands), manages session/context compaction — inherited, unmodified
- **Provider layer:** sends/receives chat completion requests — inherited; VanGio only supplies configuration (which providers, which is default), not new code here
- **Local filesystem/git:** snapshot-based undo, config storage (`opencode.json`, `auth.json`) — inherited

## 3. Provider Contract (shared across GLM/Qwen/Kimi/Ollama)

```typescript
interface ChatCompletionRequest {
  model: string;                    // e.g. "glm-4.7-flash"
  messages: Array<{ role: 'system'|'user'|'assistant'|'tool'; content: string; tool_call_id?: string }>;
  tools?: Array<{ type: 'function'; function: { name: string; description: string; parameters: object } }>;
  stream?: boolean;
}

interface ChatCompletionResponse {
  choices: Array<{
    message: { role: 'assistant'; content: string | null; tool_calls?: Array<{ id: string; function: { name: string; arguments: string } }> };
    finish_reason: 'stop' | 'tool_calls' | 'length' | 'content_filter';
  }>;
  usage: { prompt_tokens: number; completion_tokens: number; total_tokens: number };
}
```

## 5. Key Data Flows

### Flow: Main coding session
1. User types a prompt in the terminal
2. Agent core sends `ChatCompletionRequest` to active provider (GLM by default)
3. Response may include `tool_calls` → agent core executes them (file edit / shell command) locally
4. Result fed back to the model as a `tool` message → loop continues until `finish_reason: stop`
5. Final response streamed to terminal

### Flow: Rate-limit / provider switch
1. Provider returns HTTP 429 or "overload" error
2. Agent core catches error → **(new VanGio behavior, not inherited)** shows clear message: "GLM is rate-limited — switch provider with `/models`"
3. User manually switches to Qwen/Kimi/Ollama
4. Session continues with new provider — context/history preserved

## 6. Third-Party Integrations

| Provider | Auth method | Failure handling |
|---|---|---|
| GLM (Zhipu) | API key via `{env:ZHIPU_API_KEY}` | 429/throttle → surface clear error (new behavior) |
| Qwen (Alibaba) | API key | Same |
| Kimi (Moonshot) | API key, requires $1 min top-up | Same, plus known "temporary engine overload" errors |
| Ollama | None (local) | Connection refused if not running → clear message to start Ollama |

---

## 7. Performance Notes
- Context compaction: inherited from OpenCode, not rebuilt
- No caching layer needed (single local user, no shared state)
- Known constraint: local Ollama on current hardware (16GB RAM, integrated graphics) will be slow — documented in BRD

---

## 8. Error Taxonomy

| Category | Example | Behavior |
|---|---|---|
| Rate limit | GLM/Kimi 429 | Clear message + suggest provider switch (Must Have) |
| Connection | Ollama not running | Clear message, no crash |
| Tool-calling quirk | Free model doesn't stop cleanly after tool call | Known category issue, logged, doesn't crash session |
| Auth | Missing/invalid API key | Clear message pointing to `/connect` |
